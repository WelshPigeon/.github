This is a **private Pigeon Studios repository** for an internal project, such as a Discord bot, service, website or tool. It isn't open to outside contributions, issues or pull requests. Access is limited to Pigeon Studios and people we've given access to in writing, such as contractors, and is covered by [LICENSE.md](LICENSE.md) and your agreement with us.

If you've been given access, this guide is how we work. If you've found this repository by mistake, please see section 5 of [LICENSE.md](LICENSE.md).

## Ground rules

- **Confidential.** Don't share code, screenshots, credentials, server details or anything about this repository outside Pigeon Studios.
- **No secrets in Git, ever.** See [Secrets and data](#secrets-and-data).
- **`main` is what's live.** Merging to `main` deploys, so nothing lands there without passing [Testing](#testing).
- **Never develop against live.** Use a test bot, a test Discord server and a test database.
- **Credit.** Commits, merge requests and releases go out under Pigeon Studios. Don't add co-author, "generated by" or tool attribution lines.

## Getting set up

Follow **Running it locally** in [README.md](README.md). You'll need your own development values in `.env`; ask for test credentials rather than reusing live ones.

## Branches

| Branch | Use |
|---|---|
| `main` | Live code. Protected: changes arrive through pull requests only, and every merge deploys. |
| `feat/<short-name>` | A new feature |
| `fix/<short-name>` | A bug fix |
| `hotfix/<short-name>` | An urgent fix for a live problem |
| `chore/<short-name>` | Tooling, CI, dependencies, docs |

Keep branches short-lived. Bring `main` into your branch before opening a pull request if it has moved.

## Commits

We use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `chore:`, `ci:`, and `!` for breaking changes (`feat!: …`). Write the first line in the imperative mood, under 72 characters, and explain the why in the body when it isn't obvious.

## Pull requests and review

- Open a pull request (merge request on GitLab) into `main` and fill in the template.
- Every pull request is reviewed by the code owner before merging.
- Squash-merge, with a Conventional Commit title.
- Add an entry under **Unreleased** in `CHANGELOG.md` for anything users of the bot or service would notice.
- If you add an environment variable, add it to `.env.example` (placeholder value) and the table in `README.md` in the same pull request, and tell the owner so the CI secret and host setting can be added **before** merging.

## Secrets and data

- Secrets (bot tokens, API keys, Stripe keys, webhook URLs, database passwords, SFTP and SSH credentials) live **only** in:
  - a local `.env` file, which is in `.gitignore`;
  - GitHub Actions secrets or GitLab CI/CD variables (masked and protected); or
  - the host's environment settings.
- `.env.example` lists every variable with **placeholder values only**, for example `DISCORD_TOKEN=your-bot-token-here`. Never copy a real `.env` to `.env.example`.
- If a secret is ever committed, even to a branch, even for a minute: **revoke and replace it immediately**, then remove it from the code. Deleting the commit doesn't make it safe; treat the old value as public.
- Never commit customer, member or player personal data, database dumps or production logs. Use made-up test data.
- Turn on GitHub **secret scanning** and **push protection** for the repository where available.
- Personal data the project stores must be listed in the **Data and privacy** section of `README.md` and covered by our [Privacy Policy](https://pigeonstudios.co.uk/legal/privacy/).

## Coding standards

### JavaScript and Node.js

- Use modern JavaScript: `const` and `let`, `async`/`await`, no callbacks where a promise is available.
- 2-space indentation, semicolons, single quotes, as set by `.editorconfig` and the existing code.
- Handle every rejected promise. An unhandled rejection can crash the bot.
- Read configuration from environment variables once, at start-up, and fail with a clear message if a required one is missing.
- Log with enough context to debug from production logs, but never log tokens, keys or personal data.
- Respect Discord's rate limits; don't send messages or API calls in tight loops.

### Discord

- Register slash commands with the narrowest permissions they need (`setDefaultMemberPermissions`), and check permissions again in the handler.
- Reply or defer within 3 seconds; use `deferReply()` for anything slow.
- Validate every option a user can type. Treat user input as untrusted, especially anything that ends up in a database query, a file path or an embed.

### Lua (if the project includes FiveM code)

The [public contributing guide](https://github.com/WelshPigeon/.github/blob/main/CONTRIBUTING.md#coding-standards) applies: validate every server event, keep secrets server-side, parameterised queries only.

## Dependencies

- Add a dependency only when it's clearly worth it, and prefer well-maintained packages.
- Commit `package-lock.json`, and install with `npm ci` in CI and deployment.
- Keep dependencies updated; review Dependabot or Renovate pull requests promptly, and read the changelog before merging a major version.

## Testing

Before merging:

- [ ] it runs locally against a test bot and test server with no errors in the logs;
- [ ] every command and feature you changed works, including permission checks and error paths;
- [ ] start-up works with a fresh `.env` built from `.env.example`;
- [ ] database changes work on a fresh database and on a copy of the current schema; and
- [ ] CI passes.

## Versioning and releases

We use [Semantic Versioning](https://semver.org/) in `package.json`. When releasing:

1. Update `version` in `package.json`.
2. In `CHANGELOG.md`, rename **Unreleased** to `[x.y.z] - YYYY-MM-DD` and add a new empty **Unreleased** section.
3. Commit as `chore(release): vx.y.z`, merge it, and tag the merge commit `vx.y.z`.

## Deploying

1. Merging to `main` deploys automatically through the workflow in `.github/workflows/` (or `.gitlab-ci.yml`), using secrets from CI variables.
2. Watch the workflow run and the host's logs until the bot or service reports it's healthy.
3. Check the main features work in production.

## If something goes wrong

1. **Roll back:** re-run the deploy workflow on the previous release tag.
2. **Investigate** on a `hotfix/` branch, not on the server.
3. **Leaked secret:** revoke it at the source (Discord Developer Portal, Stripe dashboard, host panel), update the CI secret and host setting, and redeploy.
4. **Personal data exposed:** tell the owner straight away. Under UK GDPR, some data breaches must be reported to the ICO within 72 hours.
