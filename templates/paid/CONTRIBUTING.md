If you've been given access, this guide is how we work. If you've found this repository by mistake, please don't use, copy or share anything in it. Delete any copies and tell us at pigeon@pigeonstudios.co.uk.

## Ground rules

- **Confidential.** Don't share code, screenshots, credentials or details of this repository outside Pigeon Studios.
- **No secrets in Git, ever.** See [Secrets and data](#secrets-and-data).
- **`main` is always releasable.** Nothing lands on `main` without passing the checks in [Testing](#testing).
- **Credit.** Commits and releases go out under Pigeon Studios. Don't add co-author, "generated by" or tool attribution lines to commits, pull requests or releases.

## Branches

| Branch | Use |
|---|---|
| `main` | The released code. Protected: changes arrive through pull requests only. |
| `feat/<short-name>` | A new feature |
| `fix/<short-name>` | A bug fix |
| `hotfix/<short-name>` | An urgent fix for a live problem, released as a patch straight away |
| `chore/<short-name>` | Tooling, CI, dependencies, docs |

Keep branches short-lived. Rebase on `main` or merge it in before opening a pull request if `main` has moved.

## Commits

We use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `locale:`, `chore:`, and `!` for breaking changes (`feat!: …`). First line in the imperative mood, under 72 characters; explain the why in the body when it isn't obvious.

## Pull requests and review

- Open a pull request into `main` and fill in the template.
- Every pull request is reviewed by the code owner (see `.github/CODEOWNERS`) before merging.
- Squash-merge, with a Conventional Commit title.
- Add an entry under **Unreleased** in `CHANGELOG.md` for anything a customer would notice.
- Don't bump the version in a feature pull request; that happens in the release step.

## Secrets and data

- Secrets (bot tokens, API keys, Stripe keys, webhook URLs, database passwords, SFTP credentials) live **only** in:
  - a local `.env` file, which is in `.gitignore`;
  - GitHub Actions secrets or GitLab CI/CD variables (masked and protected); or
  - the host's environment settings.
- `.env.example` lists every variable **with placeholder values only**, for example `DISCORD_TOKEN=your-bot-token-here`.
- If a secret is ever committed, even to a branch, even for a minute: **revoke and replace it immediately**, then remove it from the code. Deleting the commit doesn't make it safe; the old value must be treated as public.
- Never commit customer or player personal data, database dumps or production logs. Use made-up test data.
- Turn on GitHub **secret scanning** and **push protection** for the repository where available.

## Coding standards

The public [contributing guide](https://github.com/WelshPigeon/.github/blob/main/CONTRIBUTING.md#coding-standards) sets out our Lua, JavaScript, security, configuration, locale, database and NUI standards. They apply here too. In particular:

- never trust the client: validate every server event;
- keep secrets server-side;
- parameterised queries only; and
- check native signatures against the [native reference](https://docs.fivem.net/natives/).

## Escrow

- Everything buyers may edit (configuration, locales, bridge files, SQL and documentation) is listed under `escrow_ignore` in `fxmanifest.lua`. Everything else is escrowed.
- Keep secrets and anti-abuse logic in escrowed server files, never in `escrow_ignore` files.
- Bridge files are visible to buyers: keep them clean, commented and free of anything you wouldn't want copied.
- When you add a file, decide straight away whether it's escrowed, and update `escrow_ignore` in the same pull request.
- Internal notes, build steps and anything not for buyers go in `docs/INTERNAL.md`, which `.gitattributes` keeps out of release zips.

## Testing

Before merging, on a development server:

- [ ] the resource starts with no errors or warnings in the server console or F8 console;
- [ ] the change works on every supported framework and inventory listed in `README.md`;
- [ ] a fresh install from `sql/install.sql` works, and so does upgrading an existing database with the new migration;
- [ ] configuration from the previous release still works, or the change is marked as breaking with upgrade notes;
- [ ] `resmon` shows no new idle cost on the client or server; and
- [ ] before a release, the **escrowed build** downloaded from the Cfx.re Portal has been tested on a clean server, not only the source.

## Releasing

1. Make sure `main` is up to date and passes [Testing](#testing).
2. Decide the version using [Semantic Versioning](https://semver.org/). A change buyers must act on is a major version.
3. Update `version` in `fxmanifest.lua`.
4. In `CHANGELOG.md`, rename **Unreleased** to `[x.y.z] - YYYY-MM-DD`, add **Upgrade notes** if buyers need to do anything, add a new empty **Unreleased** section, and update the links at the bottom.
5. Commit as `chore(release): vx.y.z`, merge, and tag the merge commit `vx.y.z`.
6. Build the release zip with `git archive` (which leaves out files marked `export-ignore`) and upload it to the Cfx.re Portal (Keymaster) as a new version of the asset.
7. Download the escrowed build from the Portal and test it on a clean server.
8. Update the Tebex package description and screenshots if anything visible changed.
9. Update the resource's entry in the public version registry (`pigeon-resource-versions`) so buyers' update checkers see the new version.
10. Post the release notes in the Discord announcements channel.

## Support and hotfixes

- Bugs reported by buyers are tracked as issues in this repository, with the order number recorded in the ticket, not in the issue.
- A fix for a problem stopping buyers from using the resource is released as a patch as soon as it's tested, through a `hotfix/` branch.
- Security fixes follow the [Security Policy](https://github.com/WelshPigeon/.github/blob/main/SECURITY.md) timelines.
